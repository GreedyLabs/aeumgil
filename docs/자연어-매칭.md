# 자연어 목적 입력과 테마 키워드 매칭

현재 목적 입력은 **DB 테마 목록 한 번 조회 + 단어 기반 순수 계산**으로 동작한다. 로그인 사용자는 세션 소유자의 저장 취향을 추가로 읽어 명시 조건이 동등한 후보 사이에만 참고한다. 미로그인은 기존 공개 키워드 검색을 그대로 사용한다. `EUMGIL_AGENT_LLM` 값과 무관하게 검색 입력을 LLM으로 보내지 않는다. 검색을 위해 코스·날씨·혼잡 API를 호출하지 않으며 이전 검색의 영속 캐시도 사용하지 않는다. 추천 코스를 여는 이후 단계의 동적 보강과는 별개다.

홈과 결과의 입력 수정은 공통 [ThemeQueryInput](../apps/web/src/components/theme-query-input.tsx)의 한 줄 입력을 사용한다. Enter 또는 검색 버튼으로 폼을 제출하며 빈 입력은 제출하지 않는다. 한글 조합 중 Enter와 키 코드 229는 조합 확정으로 처리해 검색이 먼저 실행되지 않게 한다. 모바일 키보드에는 검색 동작을 안내한다.

## 키워드 사전

[theme-keywords.ts](../apps/web/src/domain/theme-keywords.ts)의 `THEME_KEYWORD_TOPICS`가 10개 활동·분위기를 정의한다.

| 분류 ID    | 대표 표현                        |
| ---------- | -------------------------------- |
| `sea`      | 바다·해변·항구·일출·오션뷰·beach |
| `mountain` | 산·등산·트레킹·설악산·hiking     |
| `local`    | 시장·먹거리·미식·해산물·market   |
| `cafe`     | 카페·커피·사진·전망·coffee       |
| `culture`  | 미술관·박물관·전시·실내·museum   |
| `heritage` | 역사·사찰·문화재·한옥·temple     |
| `forest`   | 숲·산책·수목원·휴양림·forest     |
| `nature`   | 계곡·폭포·동굴·호수·nature       |
| `family`   | 가족·아이·체험·목장·kids         |
| `quiet`    | 조용·한적·휴식·힐링·quiet        |

각 항목의 역할은 다음과 같다.

- `keywords`: 사용자가 입력할 수 있는 표현과 동의어.
- `metadata`: DB 테마 제목·태그·무드에서 해당 분류를 판별할 단어.
- `themeIds`: 기존 개별 큐레이션 테마와 직접 연결.
- `weight`: 활동과 분위기의 상대 점수. 측정된 정확도나 추천 성공 확률이 아니다.

지역 추천 `gangwon-<지역>-<분류>`는 같은 분류 사전을 공유한다. `THEME_EXTRA_KEYWORDS`에 테마 ID별 추가 표현을 넣을 수 있다. 제목·태그·무드의 직접 일치도 사용하므로 새로운 테마의 실제 메타데이터를 정확히 유지해야 한다.

## 매칭 흐름

[matching.ts](../apps/web/src/domain/matching.ts)의 `rankCatalogThemes`가 다음을 수행한다.

1. 입력 공백·대소문자를 정리하고 `international-intent.ts`의 영어·중국어 간체/번체·일본어·독일어·프랑스어 여행 단어를 정본 키워드로 옮긴다. 원문 입력은 보존한다. 명시된 한국어 조사·활용형·복합어를 처리한다.
2. 18개 시군과 긍정/제외 활동 단어를 찾는다. 영어는 단어 경계를 사용하며 ‘부산’, ‘계산’을 ‘산’으로 오인하지 않는다.
3. 명시한 지역 밖의 후보와 제외 조건에 걸린 후보를 제거한다.
4. 남은 후보의 분류 점수·직접 단어 증거와 명시한 일수의 일치 보조 점수로 정렬하고 대표·대안과 설명을 반환한다. 동점인 경우 저장한 관심 분야, 지역 대표 코스, ID 순으로 보조 정렬한다. 저장 취향이 더 강한 단어 증거나 제외·지역 조건을 덮어쓰지 않는다.

‘강릉바다여행’ 같은 명시 복합어, ‘바다 말고 숲’, ‘카페는 빼고’, 영어 `without` 등 한정된 표현을 처리한다. 형태소 분석기나 범용 언어 이해 모델은 아니며 복잡한 부정·역설·오타·대화 문맥까지 이해한다고 표시하지 않는다.

지역에 원하는 활동 후보가 부족하면 다른 지역으로 조용히 바꾸지 않는다. 지역 후보가 있지만 활동 일부가 빠졌다면 부분 일치로 안내한다. 여러 지역을 입력한 결과는 후보 비교이지 모든 지역을 한 코스에 연결했다는 뜻이 아니다.

## 결과 계약

`ThemeMatch`에는 `primaryId`, `altIds`, `explanation`이 있다. 설명은 `status`, `keywords`, `excludedKeywords`, `regions`, `summary`, 선택적 `notice`, 취향 보조 정렬을 참고했을 때의 `preference` 안내로 구성한다.

| 상태        | 의미                                              | UI에서 지킬 것                                               |
| ----------- | ------------------------------------------------- | ------------------------------------------------------------ |
| `matched`   | 분류·단어가 일치함                                | 어떤 단어·지역으로 골랐는지 설명                             |
| `partial`   | 활동 일부가 빠졌거나 별도 확인이 필요한 조건      | 누락·확인 조건을 함께 표시                                   |
| `unmatched` | 빈 입력·무관한 입력·긍정 조건 없음·유효 후보 없음 | `primaryId=""`, 대안 빈 배열. 임의 테마로 자동 이동하지 않음 |

실내 요청은 문화 테마에 야외 장소가 섞일 수 있음을 알린다. 조용한 분위기는 실제 혼잡 보장이 아니고, 휠체어/유모차·반려동물 조건은 장소별 안내 확인이 필요하다. 사전에 단어를 추가한 사실만으로 장소의 이용 가능성을 인증하지 않는다.

결과 화면은 공통 내비게이션을 유지하고 근거 키워드·제외어·부분 일치 안내를 보여준다. 입력 수정 폼을 펼쳐 다시 검색할 수 있으며 선택한 추천에서 조건을 유지해 코스로 이동한다. 결과를 숨긴 채 임의 테마로 자동 전환하지 않는다.

일수·동행·페이스·이동수단 등은 [course-options.ts](../apps/web/src/domain/course-options.ts)에서 추출해 코스 조건으로 전달한다. 추천 일수는 당일~5일이며 ‘2박3일’, ‘4일’처럼 명시한 일수를 읽는다. 검색에서는 일수가 같은 후보에 보조 점수를 주며 다른 기간을 모두 탈락시키는 필터는 아니다. 탐색의 별도 기간 필터는 해당 기본 기간과 정확히 일치하는 테마만 보여준다.

텍스트에서 명시된 조건만 추출하며, 추천 코스를 만들 때 비어 있는 페이스·동행에만 저장 취향을 보충한다. 실제 합쳐진 조건은 `Course.appliedOptions`로 화면과 개인 코스 복사 링크에 전달한다. 개인 코스의 임의 실제 날짜 범위·날짜 미정 일차는 추천 일수 1~5일과 별개다. 매칭 결과를 여행 전체의 실행 가능성 판정으로 해석하지 않는다.

## 여행 취향 설정

[/onboarding](../apps/web/src/components/screens/onboarding.tsx)은 공통 메뉴를 유지하는 로그인 사용자용 설정 화면이다. 저장된 선택을 복원하며 관심 분야·페이스·동행에 임의의 최초 값을 넣지 않는다. 모두 선택 사항이고, ‘선택 비우기’ 후 저장하면 설정을 해제할 수 있다. 닉네임·소개 편집은 취향을 생성하거나 덮어쓰지 않는다.

[travel-preferences.ts](../apps/web/src/domain/travel-preferences.ts)의 10개 관심 분야는 검색 사전과 같은 `topic:sea` 등의 안정 코드를 기존 `onboarding_preference.interest_theme_ids` JSON 배열에 저장한다. 계속 늘어나는 개별 여행 코스 대신 관심 분야를 고르게 한다. 기존 큐레이션 ID와 현재 지역 코스 분류는 읽을 때 변환한다. 종합 명소(`highlights`)와 알 수 없는 ID는 특정 취향으로 추정하지 않는다. DB 스키마 추가는 없다.

관심 분야는 입력 조건이 같은 후보의 순서를 정할 때만 보조한다. 입력 없는 검색이나 무관한 검색을 취향만으로 성공 처리하지 않는다. 페이스·동행은 명시하지 않은 추천 코스 조건에만 쓰며 적용 안내를 보여준다. 실제 혼잡, 영업시간, 접근 가능성을 보장하지 않는다.

Repository는 공유 인스턴스라도 취향을 저장해 두지 않는다. 요청마다 현재 세션 소유자로 조회하고 사용자 취향·개인화 결과를 공개 API 캐시에 넣지 않는다. 저장 실패는 오류로 반환하며, 저장 후 프로필·설정·검색·추천 코스의 재검증을 요청한다.

순수 조건/구형 ID 호환은 [도메인 테스트](../apps/web/src/domain/travel-preferences.test.ts), 세션 소유자·실패·프로필 편집 분리는 [액션 테스트](../apps/web/src/app/actions/travel-preferences.test.ts), 요청별 사용자 격리와 코스 배선은 [Repository 테스트](../apps/web/src/data/live/travel-preferences.test.ts)로 검증한다. 실행·배포 여부는 [검증 기록](검증.md)을 따른다.

## 키워드 추가와 검증

1. 공통 표현이면 해당 topic의 `keywords`, 특정 테마만의 표현이면 `THEME_EXTRA_KEYWORDS`에 넣는다.
2. 새 테마의 분류가 자동 연결되지 않으면 ID/metadata와 실제 구성 장소를 대조한다.
3. [catalog-matching.test.ts](../apps/web/src/domain/catalog-matching.test.ts)에 긍정·부정·지역 제한·단어 경계 회귀 사례를 추가한다. 한국어 합성어와 영문도 함께 점검한다.
4. [match-guard.test.ts](../apps/web/src/data/live/match-guard.test.ts)로 검색 단계의 LLM·동적 API 호출이 없는 계약을 유지한다.
5. 브라우저에서 일치·부분 일치·미일치의 설명, 입력 수정, 추천 선택 뒤 일정 조건 전달을 확인한다.

사전 규칙은 운영자 의도를 설명하고 재현하기 쉽다. 지원하지 않는 표현은 명시적으로 보완해야 한다는 한계가 있으므로 실제 검색 사례를 바탕으로 범위를 늘린다.

## 외국어 입력

7언어 UI와 동일한 언어군의 사전 기반 약식 검색이다. `江陵海边`, `江陵海邊`, `江陵の海辺`, `Gangneung Strand`, `Gangneung plage` 등을 같은 강릉 바다 테마에 연결한다. 명시한 `不要/ohne/sans/…には行きたくない` 제외 표현을 반영하고 라틴 단어 내부는 매칭하지 않는다. 일수·동행·대중교통 등도 사전에 있는 표현만 읽는다. 번역 모델이 아니므로 임의 문장이나 알려지지 않은 지역·표현을 모두 이해하지 않는다. 공식 관광정보 API 번역은 장소 표시용이며 검색 문장을 외부 번역 API로 전송하지 않는다.
