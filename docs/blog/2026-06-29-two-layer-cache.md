# 서버 재시작을 견디는 API 응답 캐시 설계: 메모리와 파일 2층 구조

공공 API를 호출하는 서버에서 가장 흔히 겪는 문제 중 하나는 캐시가 프로세스와 함께 사라진다는 점입니다. 모듈 스코프의 `Map` 하나로 시작한 캐시는 서버를 배포하거나 재시작하는 순간 전부 날아가고, 콜드스타트 때마다 외부 API를 다시 긁어야 합니다. 이 글은 그 문제를 메모리와 파일을 함께 쓰는 2층 구조로 해결한 과정을 정리한 기록입니다. 비슷한 서버 캐시 요구를 가지신 분들께 참고가 되었으면 합니다.

에움길은 기상청, 에어코리아, 한국관광공사 등 7종의 공공 API를 실시간으로 호출합니다. 날씨나 대기질 데이터는 10분, 관광지 상세정보는 24시간 정도의 TTL이면 충분합니다. 처음에는 모듈 레벨 `Map`으로 캐시를 만들었는데, 개발 중 저장 서버를 재시작할 때마다 모든 캐시가 사라지고 API를 다시 호출하는 것이 번거로웠습니다. 더 중요하게는, 실제 배포 환경에서 콜드스타트 직후 다수의 요청이 몰리면 API 호출이 폭발할 수 있다는 점이 문제였습니다.

## 2층 구조를 선택한 이유

가장 단순한 해결책은 Redis 같은 외부 캐시 서버를 두는 것입니다. 하지만 공모전 제출 서비스에 외부 의존성을 하나 더 추가하는 것은 부담이었습니다. 데이터베이스가 없어도 동작해야 하는 mock 모드도 고려해야 했습니다. 그래서 "영속성은 로컬 파일로, 속도는 메모리로"라는 방향을 잡았습니다.

설계 원칙은 간단합니다.

- **읽기**: 메모리를 먼저 확인하고, 없으면 파일 스냅샷을 로드해서 채운다.
- **쓰기**: 메모리에 즉시 반영하고, 잠시 후 파일에 flush한다.
- **만료**: 엔트리는 값과 생성 시각만 저장하고, 신선도 판단은 호출 시 TTL로.
- **정리**: flush 시 maxAge를 초과한 엔트리는 자동 제거한다.

## 핵심 인터페이스: 백엔드를 주입 가능하게

구현의 핵심은 `CacheStore` 인터페이스입니다.

```ts
export interface CacheStore {
  load(): Promise<Record<string, CacheEntry>>;
  save(entries: Record<string, CacheEntry>): Promise<void>;
}
```

파일 백엔드(`fileStore`)와 인메모리 백엔드를 모두 이 인터페이스로 표현합니다. 덕분에 실제 앱은 파일 백엔드를 쓰고, 단위 테스트는 인메모리 백엔드를 주입해서 파일 I/O 없이 돌릴 수 있습니다. Vitest에서 `setSystemTime`으로 시각을 조작할 때 실제 캐시 파일이 끼어들어 오래된 엔트리가 신선한 것처럼 보이는 버그를 이 구조로 막을 수 있었습니다.

## 디바운스 flush로 쓰기 폭주 방지하기

파일 쓰기는 매 캐시 SET마다 하지 않습니다. 대신 타이머를 예약해두고, 일정 시간(기본 2초) 안에 새 SET이 오면 타이머를 연장합니다. 요청이 몰릴 때 수십 번의 파일 쓰기가 한 번으로 합쳐지는 효과입니다.

```ts
function scheduleFlush(): void {
  dirty = true;
  if (timer) return;          // 이미 예약됨 → 덮어쓰지 않음
  timer = setTimeout(() => {
    timer = null;
    void flush();
  }, flushDelayMs);
  (timer as { unref?: () => void }).unref?.();  // 타이머가 프로세스 종료를 막지 않도록
}
```

`.unref()` 한 줄이 중요합니다. 이 타이머가 살아 있는 동안에는 Node.js 프로세스가 종료되지 않기 때문에, `unref`로 "이 타이머 때문에 살아있지 않아도 된다"고 표시해둡니다. 테스트나 배포 종료 시 프로세스가 멈추는 현상을 막기 위해서입니다.

## 파일 로드는 한 번만

서버 시작 직후 여러 요청이 동시에 들어오면, 파일 로드도 여러 번 실행될 수 있습니다. `loading` Promise를 보관해두고 이미 로드 중이면 같은 Promise를 기다리도록 했습니다.

```ts
async function ensureLoaded(): Promise<void> {
  if (loaded) return;
  if (!loading) {
    loading = store.load().then(/* 메모리에 병합 */).finally(() => { loaded = true; });
  }
  await loading;
}
```

파일에서 읽은 엔트리를 메모리에 병합할 때, 이미 메모리에 있는 키는 덮어쓰지 않습니다. 파일보다 메모리가 항상 최신이기 때문입니다.

## 최종 사용: 한 줄로 감싸기

호출부에서 보이는 인터페이스는 `cached(key, ttlMs, fn)` 하나입니다.

```ts
const weather = await apiCache.cached(
  `weather:${lat}:${lon}`,
  10 * 60 * 1000,   // 10분 TTL
  () => fetchWeatherFromKma(lat, lon),
);
```

HIT이면 캐시값을 즉시 반환하고, MISS면 `fn()`을 실행해 저장합니다. 호출부는 캐시 존재 여부를 전혀 신경 쓸 필요가 없습니다.

## 마치며

공공 API 응답 캐시를 2층으로 나눠보니, 서버 재시작 후에도 이전 응답을 재활용할 수 있게 됐고 테스트 격리도 자연스럽게 따라왔습니다.

교훈을 정리하면 이렇습니다. 첫째, 캐시 백엔드를 인터페이스로 추상화하면 프로덕션과 테스트에서 같은 캐시 로직을 다른 저장소로 구동할 수 있습니다. 둘째, 디바운스 flush는 쓰기 폭주를 막는 가장 간단한 방법이지만, `.unref()`를 빠뜨리면 프로세스 종료가 지연되는 함정이 있습니다. 셋째, 파일 I/O는 베스트 에포트로 다루는 것이 맞습니다. 쓰기 실패를 예외로 던지지 않고 조용히 넘기면, 파일 시스템 문제가 생겨도 메모리 캐시는 계속 동작합니다.

같은 요구를 가지신 분들께 참고가 된다면 더할 나위 없겠습니다. 궁금한 점이나 더 나은 방법이 있으면 편하게 알려주세요.
