# 후보 3 — 답변 보류(abstention): 근거 부족·API 실패 시 결정형 폴백/사람 위임

> **포지션: 후보 1의 평가축으로 편입 권장.** 단독 워크플로우로는 얇다. 독립 제출용으로 정리하되, 실제로는 후보 1의 성공/실패 기준(폴백률·보류 정확도)으로 흡수하는 것이 낫다.

## 1. 문제 정의 (Week 1)

### 사용자 / 업무
- **사용자**: 코스 추천을 받는 방문자(간접) + 서비스 신뢰도를 지켜야 하는 운영자.
- **업무**: 혼잡/날씨/대기질 데이터가 없거나 LLM 신뢰도가 낮을 때 **추천을 밀어붙이지 않고** 결정형 로직/사람에게 위임(abstention)할지 판단한다.
- 이미지 예시의 "답변 보류: 근거 부족·이미지 훼손 시 사람에게 넘기기"에 대응(에움길 맥락에선 '이미지 훼손' 대신 'API 실패·데이터 결측').

### 입력 / 출력
- **입력**: 의도 + (부분적으로 결측/실패한) 도구 컨텍스트.
- **출력(schema)**:
  ```
  DeferDecision {
    action: "answer" | "fallback" | "defer_to_human"
    reason: str
    confidence: float
  }
  ```

### 데이터 출처
- 정상 케이스 + **장애 주입 케이스**(API 타임아웃/빈 응답/모순 데이터) — mock ToolContext로 결함을 주입해 합성.

### 성공 / 실패 기준
- **성공**: 근거가 충분하면 답하고, 부족하면 정확히 폴백/보류. 즉 **불필요한 보류(과잉 회피)와 위험한 강행(과소 회피)을 동시에 낮춤**.
- **실패**: 근거 부족한데 강행(환각 추천) / 충분한데 과도하게 보류(효용 손실).
- **핵심 지표**: false-answer율, over-defer율, 폴백 발동 정확도.

## 3. 왜 단독보다 편입인가
- 에움길 플래너는 이미 4겹 가드레일 실패 시 `source:"fallback"`으로 무중단 복귀한다([planner.ts](../../apps/web/src/server/agent/planner.ts)). 즉 **abstention 메커니즘이 이미 제품에 내장**돼 있다.
- 보류는 독립된 "업무"라기보다 **모든 에이전트 워크플로우가 가져야 하는 평가 차원(축)**이다. 후보 1의 성공/실패 기준에 `폴백률`·`보류 정확도`를 추가하면 한 프로젝트로 둘 다 검증된다.
- **그럼에도 독립 제출 가치**: "verifiable"의 가장 어려운 부분이 "모를 때 모른다고 하는가"의 측정이다. 안전성 평가에 초점을 두고 싶다면 이 후보를 메인으로 삼을 수도 있다.
