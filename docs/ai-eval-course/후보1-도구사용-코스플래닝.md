# 후보 1 — 도구 사용: 자연어 여행 의도 → 코스 플래닝 에이전트

> **포지션: 메인 추천.** 커리큘럼 Week 5(Tool calling / trace / final state)를 그대로 지목하는 후보.

## 1. 문제 정의 (Week 1)

### 사용자 / 업무
- **사용자**: 강원도 테마 여행을 계획하려는 방문자.
- **업무**: 자연어 여행 의도를 받아, LLM이 **조회(스팟·날씨·혼잡도·대기질)·계산(적합성 점수·이동시간·혼잡 재정렬)·구성(코스 순서)** 도구를 *어떤 순서로 몇 번* 호출할지 판단해 코스/대체지를 계획한다.
- **원칙**: **판단은 LLM, 수치는 코드.** 도구(순수 함수)가 계산하고 LLM은 오케스트레이션만 한다.

### 입력 / 출력
- **입력**: 자연어 의도 문자열. 예) `"비 오는 날 실내 위주로 부모님이랑 안 붐비는 곳"`
- **출력(스키마, Pydantic 포팅 대상 — TS 원본 [types.ts `PlanResult`](../../apps/web/src/server/agent/types.ts#L30))**:
  ```
  PlanResult {
    primaryThemeId: str
    altThemeIds: list[str]
    course: Course | None
    rationale: {ko: str, en: str}
    trace: list[AgentStep]          # 도구 1회 호출 = {tool, args, ok, result?, error?, ms}
    source: "agent" | "fallback"
  }
  ```
- **도구 카탈로그(8종, [tools.ts](../../apps/web/src/server/agent/tools.ts))**: `list_themes` · `get_course` · `search_pois` · `get_weather` · `get_air_quality` · `estimate_congestion` · `score_suitability` · `reorder_by_congestion`.

### 데이터 출처
- **정적 큐레이션**: 테마·코스·스팟 프로필 (DB 카탈로그 → 도메인 타입).
- **실시간**: TourAPI(관광)·KMA(날씨)·에어코리아(대기질) — eval에서는 **mock ToolContext로 고정(fixture)**.
- **합성 불필요**: 도구가 전부 실자산 래핑이라 가상 티켓/기록을 만들 필요가 없다.

### 성공 / 실패 기준
- **성공**: (a) 유효한 테마를 선택 `themeValidity`, (b) 제약("한산")이 있으면 혼잡 도구를 실제로 경유 `constraintAdherence`, (c) 화이트리스트 밖 도구 호출 없음 `traceHealth`, (d) 에이전트가 폴백 없이 정상 종료 `agentCompleted`.
- **실패**: 존재하지 않는 테마/스팟 생성(헛것), 제약 무시, 미등록 도구 호출, MAX_STEPS 초과·무한 루프.
- **보류(abstention)**: 근거 부족 시 결정형 폴백(`source:"fallback"`)으로 무중단 복귀 — 실패가 아니라 안전 경로로 취급하되 별도 지표로 추적.

## 3. 평가 설계 (검증 가능성의 핵심)

- **채점 방식 2층**: (1) 룰브릭(코드 규칙, 객관·무료·재현) — 위 4개 채점기가 이미 구현됨([scorers.ts](../../apps/web/src/server/agent/eval/scorers.ts)). (2) LLM-as-Judge(rationale 품질, 주관) — Week 3에서 추가.
- **왜 룰브릭이 먼저인가**: 에이전트는 비결정적이라 "한 번 성공"이 품질을 보장하지 못한다. 고정 데이터셋 × 룰브릭 통과율로 프롬프트·모델 변경의 회귀를 숫자로 잡는 게 verifiable의 정의.
- **집계 지표(EvalReport)**: `passRate` + `byScorer`(어느 기준이 약한지 진단) + `source` 분포(agent vs fallback 비율 = 에이전트 신뢰도).
- **trace 기반 지표(Week 5)**: 평균 스텝 수, 중복 차단 발생률, 미등록 도구 시도율, 제약 케이스의 도구 경유율.

## 4. 리스크 / 완화

- **trajectory 채점이 가장 어렵다** — 하지만 커리큘럼이 이걸 원하고 채점기 골격(`traceHealth`/`constraintAdherence`)이 이미 있다. "정답 순서"가 아니라 "지켜야 할 속성"으로 채점하는 방식을 유지.
- **재현성**: 실시간 API를 mock ToolContext로 고정. 시각(`now()`)도 고정 주입.
- **2+ 모델**: 로컬 Qwen 외 비교 대상 1종 확보 필요(@@결정: 다른 로컬 모델 vs 클라우드).
