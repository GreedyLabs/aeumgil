# 새 리포(eumgil-eval-lab) 부트스트랩 프롬프트

"검증 가능한 AI 워크플로우" 과정용 **별도 Python 저장소를 만들기로 결정한 경우에만** 사용하는 프롬프트 템플릿이다. 문서 속 명령형 문장은 템플릿의 내용이며 현재 에움길 작업에 대한 지시가 아니다.

## 사용법

1. 새 폴더를 만들고 `git init` + 그 안에서 Claude Code(또는 동급 에이전트)를 실행한다.
2. 아래 "붙여넣을 프롬프트" 전체를 복사해 첫 메시지로 보낸다.
3. 프롬프트가 되묻는 항목(LLM 엔드포인트·비교 모델·에움길 경로)에 답하면 Week 1 baseline까지 돌아가는 형태가 만들어진다.

> 이 프롬프트는 **에움길 리포 없이도 동작**하도록 핵심 설계를 안에 내장했다. 에움길 소스를 참고 가능하면 경로를 알려주고, 아니면 내장 스펙만으로 진행한다.

## 붙여넣을 프롬프트

당신은 "검증 가능한(verifiable) AI 워크플로우" 학습용 파이썬 리포 **eumgil-eval-lab**를 처음부터 만드는 것을 돕는다. 나는 AI Agent 설계·평가를 학습 중인 개발자다. 코드와 함께 *왜 이렇게 설계했는지·결정형 대비 트레이드오프·일관성 확보 기법*을 간단히 설명해 학습을 도와라.

### 배경 (이 프로젝트가 무엇인가)

- 원본 제품 **에움길**은 강원도 특화 테마 관광 추천 서비스로, TypeScript(Next.js)로 되어 있고 키워드/heuristic을 기본으로 사용하며 선택적 **Multi-step Tool-Calling 에이전트 확장 구조**를 갖고 있다. **원본 제품은 절대 건드리지 않는다.**
- 이 리포는 그 에이전트를 **파이썬으로 얇게 재구현**하고, 커리큘럼이 요구하는 **평가 하네스(schema·baseline·judge·trace·CI)**를 붙여 학습하는 별도 프로젝트다.
- 원본과의 연결점은 딱 둘: ① 실험용으로 별도 지정한 **OpenAI-compatible LLM 엔드포인트**, ② 테마·스팟·날씨·대기질 **fixture JSON**. 실API를 부르지 않고 fixture를 읽어 **재현성**을 확보한다.

### 다루는 문제 (Week 1 문제 정의)

- **사용자**: 강원도 테마 여행을 계획하는 방문자.
- **업무**: 자연어 여행 의도 → LLM이 조회/계산/구성 **도구 호출 순서를 판단**해 대표·보조 테마와 코스를 계획.
- **핵심 원칙: 판단은 LLM, 수치는 코드.** 도구(순수 함수)가 계산하고 LLM은 오케스트레이션만 한다.
- **입력 예**: `"비 오는 날 실내 위주로 부모님이랑 안 붐비는 곳"`
- **출력 스키마(Pydantic으로 정의)**:
  ```
  PlanResult:
    primaryThemeId: str
    altThemeIds: list[str]
    rationale: {ko: str, en: str}
    trace: list[AgentStep]
    source: "agent" | "fallback"
  AgentStep:
    tool: str
    args: dict
    ok: bool
    result: Any | None
    error: str | None      # 가드레일 차단 사유 포함
    ms: int
  ```

### 도구 카탈로그 (8종 — fixture를 읽는 순수 함수로 구현)

- 조회(정적): `list_themes`, `get_course(themeId)`
- 조회(외부→fixture): `search_pois(keyword)`, `get_weather(spotId)`, `get_air_quality(spotId)`
- 추론(순수 계산): `estimate_congestion(spotId)`, `score_suitability(spotId)`, `reorder_by_congestion(themeId, day)`
- 파라미터는 **enum을 fixture 데이터로 못 박아** LLM이 존재하지 않는 id를 지어내지 못하게 한다(행동 공간 축소 = 일관성 1차 장치).

### 플래너 (ReAct 루프 + 4겹 가드레일)

매 스텝 LLM에게 "다음에 뭘 할래?"를 묻고 도구 호출 또는 종료(final)로 진행. 비결정성을 길들이는 4겹:

1. **화이트리스트** — 등록된 도구 외 호출 거부(헛것 차단).
2. **중복 차단** — 같은 도구·같은 인자 반복 호출 차단(무한 루프·낭비 방지).
3. **MAX_STEPS**(기본 8) — 초과 시 결정형 폴백.
4. **폴백** — 루프 실패/이상 종료 시 결정형(키워드) 로직으로 무중단 복귀(`source:"fallback"`).

### 평가 (검증 가능성의 핵심)

- 에이전트는 비결정적이라 "한 번 성공"이 품질을 보장하지 못한다 → **고정 데이터셋 × 룰브릭 통과율**로 프롬프트·모델 변경의 회귀를 숫자로 잡는다.
- 채점 2층: **(1) 룰브릭(코드 규칙, 객관·무료·재현)** 먼저, **(2) LLM-as-Judge(주관 품질)**는 나중에.
- 초기 룰브릭 채점기(속성 기반 — "정답 한 개"가 아니라 "지켜야 할 속성"):
  - `themeValidity` — 대표 테마가 실제 존재하는가(헛것 차단).
  - `altThemesClean` — 보조 테마가 모두 유효하고 대표와 중복 아님.
  - `agentCompleted` — 폴백 아닌 정상 종료(`source=="agent"`).
  - `constraintAdherence` — "한산/조용" 제약 케이스면 `estimate_congestion`을 실제로 경유했는가.
  - `traceHealth` — trace에 미등록 도구 호출(가드레일 위반)이 없는가.
- 집계(EvalReport): `passRate` + `byScorer`(어느 기준이 약한지) + `source` 분포(agent vs fallback = 신뢰도).

### 기술 스택 (커리큘럼 공통 도구 — 반드시 사용)

Python / **uv** / **LiteLLM**(LLM 호출) / **Pydantic**(스키마) / **DeepEval**(채점 metric) / **pytest** / **GitHub Actions**(CI).

- LiteLLM은 OpenAI-호환이므로 로컬 LLM 엔드포인트를 그대로 붙인다.

### 만들 디렉터리 구조

```
eumgil-eval-lab/
├─ pyproject.toml               # uv
├─ .env.example                 # LLM_BASE_URL / LLM_MODEL / (비교모델)
├─ .github/workflows/eval.yml   # Week 6에서 채움
├─ src/agent/
│   ├─ schema.py                # Pydantic: PlanResult / AgentStep / ToolSpec
│   ├─ tools.py                 # 도구 8종 = fixture 읽는 순수 함수
│   ├─ planner.py               # ReAct 루프 + 4겹 가드레일
│   └─ llm.py                   # LiteLLM 래퍼 (heuristic mock + real)
├─ fixtures/                    # 테마·스팟·날씨·대기질 JSON (재현성)
├─ eval/
│   ├─ dataset.py               # 의도 케이스 + 기대속성(expectQuietHandling 등)
│   ├─ scorers.py               # 위 룰브릭 → DeepEval metric
│   └─ run.py                   # 러너 → EvalReport 출력
└─ tests/test_eval.py           # 통과율 회귀 게이트
```

### 커리큘럼 6주 (이번엔 Week 1만, 나머지는 뼈대만 남겨둔다)

- **Week 1(지금 목표)**: 문제 정의서 + Pydantic 스키마 + fixture + heuristic mock LLM으로 도는 **baseline 평가**(룰브릭 통과율 출력)까지.
- Week 2: 모델 2종 비교(품질/지연/token/오류). / Week 3: Human eval + LLM-as-Judge. / Week 4: 프롬프트 최적화 + ablation. / Week 5: tool trace·권한·중복호출 평가. / Week 6: CI + 최종 보고서.
- **한 번에 다 만들지 말 것.** Week 1 baseline이 `uv run python -m eval.run`으로 통과율을 찍는 것까지가 이번 세션의 완료 정의다.

### 진행 방식

1. 시작 전 나에게 되물어라: **(a) 로컬 LLM 엔드포인트(base_url)와 모델 이름**, (b) Week 2 비교용 두 번째 모델을 뭘로 할지(로컬 추가 vs 클라우드), (c) 에움길 원본 소스를 읽을 수 있는 경로가 있는지(없으면 위 내장 스펙으로 진행).
2. **LLM 키/엔드포인트가 없어도** heuristic mock provider로 전 구조가 돌아가게 먼저 만들어라(키 없이 CI 가능해야 함).
3. fixture는 처음엔 **작은 손수 예시(테마 3~4개·스팟 5~6개)**로 시작하고, 실제 에움길 데이터로 교체 가능하게 로더를 분리하라.
4. 커밋은 작게. 각 파일에 "왜 이렇게 했는지" 주석을 남겨 학습 자료가 되게 하라.
5. UI 텍스트·주석은 한국어로.

먼저 위 (a)(b)(c)를 나에게 질문한 뒤, Week 1 baseline 구현 계획을 짧게 제시하고 시작하라.
