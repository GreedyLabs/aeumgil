# 매칭과 에이전트 레이어

운영의 기본 자연어 매칭은 **키워드 기반 결정형 방식**이다. 실 LLM은 사용하지 않는다. 코드에는 실 LLM 도구 호출·평가를 실험할 수 있는 확장 지점이 있으며 현재 서비스와 학습 실험을 구분한다.

## Repository 아래의 확장 구조

[LiveRepository](../apps/web/src/data/live/repository.ts)가 도메인 결과를 반환하며 화면은 provider 선택을 알 필요가 없다. 템플릿 조합·후보 검증·혼잡 계산·일정 시간 보정은 도메인 함수가 담당한다. 모델을 사용하더라도 실제 존재하지 않는 장소나 수치를 자유 생성하게 하지 않는다.

```text
화면 → Repository
         ├─ 키워드 매칭 / 도메인 일정 구성
         └─ 선택적 Planner → provider가 다음 도구 선택
                            → 기존 조회·계산 도구 실행
                            → trace와 최종 결과 검증
                            → 실패 시 결정형 결과
```

기본 heuristic provider는 같은 도구 계약을 코드로 결정한다. 따라서 `source: agent`라는 내부 경로 표시는 실 LLM 호출 증명이 아니다. 테스트용 scripted provider와 공개 카탈로그의 실제 운영 데이터도 서로 다르다.

## 현재 매칭

`Repository.matchThemes`는 DB 테마를 한 번 조회하고 `rankCatalogThemes` 순수 함수로 단어·지역·제외 조건을 판정한다. 검색에서는 env와 무관하게 LLM/코스/혼잡 API를 호출하지 않으며 검색 결과의 영속 캐시도 없다. 사전 10분류와 개별 테마 추가어, 일치·부분 일치·미일치 계약은 [자연어 매칭](자연어-매칭.md)에 둔다.

코스 일정 정리에는 Planner와 기본 heuristic provider를 유지한다. 실 LLM 도구 호출 실험에서 테마를 고르는 경우에도 같은 매칭 함수를 재사용한다. 이렇게 검색의 예측 가능한 비용·응답과 실험용 코스 오케스트레이션을 분리한다.

## 도구와 Planner

[tools.ts](../apps/web/src/server/agent/tools.ts)의 도구는 기존 함수와 서버 조회를 래핑한다. DB 쓰기·리뷰 수정·계정 삭제 도구는 제공하지 않는다.

| 도구                             | 책임                    |
| -------------------------------- | ----------------------- |
| `list_themes`                    | 실제 테마 후보 조회     |
| `get_course`                     | 조건을 반영한 코스 조회 |
| `search_pois`                    | 관련 관광 POI 후보 조회 |
| `get_weather`, `get_air_quality` | 날씨·대기질 조회        |
| `estimate_congestion`            | 자체 혼잡 계산          |
| `score_suitability`              | 방문 적합성 계산        |
| `reorder_by_congestion`          | 날짜별 방문 순서 조정   |

[planner.ts](../apps/web/src/server/agent/planner.ts)는 등록 도구만 실행하고 같은 도구·인자 반복과 스텝 초과(기본 8)를 제한한다. 도구 입력과 최종 테마 ID의 유효성을 검사하며 오류·종료 실패는 결정형 결과로 처리한다. 에이전트의 trace가 일정 실행 가능성을 보증하지 않으므로 최종 시간·이동 제약 검사도 유지한다.

이 분리의 장점은 모델이 바뀌어도 수치와 저장 계약을 같은 코드로 검증할 수 있다는 점이다. 비용은 도구 스키마·변환·폴백 계약을 함께 유지해야 한다는 점이다. 결정형 방식에서는 호출 비용·지연·재현성 관리가 간단하고 자유로운 문맥 이해는 제한된다.

## 선택적 실 LLM

[llm.ts](../apps/web/src/server/agent/llm.ts)에 OpenAI-compatible Chat Completions 어댑터가 있다. 실험에서 `EUMGIL_AGENT_LLM=openai`와 모델/서버를 설정한다. 로컬 호환 서버와 외부 API는 인증 요구가 다르며 실제 엔드포인트 정책에 맞춰 키를 제공한다. 운영 env에는 LLM 설정을 추가하지 않는다.

응답 JSON·도구 호출 파싱, 타임아웃, 출력 길이/문자 정리, 유효 테마 검사, 호출량·비용·지연 관리도 모델 실험에서 검증해야 한다. 기존 요청 제한 유틸리티가 실제 진입점에 연결돼 있는지도 확인한다. provider만 바꿨다는 이유로 지연이나 추천 품질 개선을 가정하지 않는다.

## 평가와 학습

[eval](../apps/web/src/server/agent/eval/)은 고정 ToolContext·시각과 룰브릭으로 provider를 비교한다. 채점기는 유효 테마·대안 무결성·정상 종료·혼잡 도구 경유·trace 권한을 검사한다. 현재 `constraintAdherence`는 실제 혼잡 감소가 아니라 특정 도구 경유를 판정하므로 제품 품질과 동일시하지 않는다.

[과거 실모델 기록](에이전트-Evaluation-리포트.md)은 작은 고정 데이터셋 실험이다. 현재 서비스의 정확도·보안·응답속도 보증이 아니다. RAG·LLM-as-judge·멀티모달·사람 위임은 운영 구현으로 간주하지 않으며 [별도 AI 학습 과정](ai-eval-course/README.md)에서 선택할 확장 주제다.
