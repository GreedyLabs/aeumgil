# 에이전트 레이어 설계 — 코스 플래닝 에이전트

> 에움길의 "자연어 → 추천" 흐름을 **결정형 파이프라인**에서 **Multi-step Tool-Calling 에이전트**로 전환하기 위한 설계 문서.
> 코드 변경 전 방향 확정용. 정본 체크리스트는 [구현-계획.md](구현-계획.md), 프로젝트 컨텍스트는 [../CLAUDE.md](../CLAUDE.md).
>
> 작성: 2026-06-23 · 상태: **설계(미구현)**

---

## 0. 왜 이 방향인가 (배경)

이 문서는 특정 AI Agent 개발자 포지션의 직무를 에움길에 매핑하면서 시작됐다. 공고의 핵심 직무는 "현장 업무에 최적화된 **Multi-step AI Agent 워크플로우 설계 및 개발**"이고, 자격요건은 **RAG · Tool Calling · 프롬프트 엔지니어링 · LLM Evaluation**의 실서비스 경험이다.

회사 도메인(현장 점검·정비·교육 + XR)은 관광과 다르다. **하지만 채용에서 검증하려는 것은 도메인 지식이 아니라 에이전트 아키텍처를 설계·상용화·운영한 경험**이며, 그 패턴은 도메인 무관하게 이전된다. 에움길은 이 패턴을 연습·증명하기에 좋은 소재다. 이유:

- 외부 도구(공공 API)와 결정형 추론 함수가 **이미 깔끔한 단위로 분리**돼 있어 tool로 노출하기 쉽다.
- CLAUDE.md에 이미 *"자연어 매칭은 키워드 우선, 후반에 LLM 검토"* 라고 적혀 있어 프로젝트 방향과 충돌하지 않는다. 이 문서는 그 "후반 LLM"을 **단순 분류가 아니라 에이전트로** 구체화하는 것이다.

## 1. 현재 구조 진단 — "에이전트가 아니다"

에움길의 추천 흐름은 지금 전부 **사람이 짠 고정 순서의 함수 호출**이다.

| 단계 | 현재 구현 | 성격 |
|---|---|---|
| 자연어 → 테마 | [`matchThemes`](../apps/web/src/domain/matching.ts) | `q.includes(keyword)` 키워드 규칙. LLM 없음 |
| 데이터 보강 | [`LiveRepository.enrich`](../apps/web/src/data/live/repository.ts) | 날씨→대기질→혼잡→적합성 **고정 순서** |
| 코스 재정렬 | [`LiveRepository.getCourse`](../apps/web/src/data/live/repository.ts) | `reorderSpotsByCongestion` 직접 호출 |

핵심 차이: **지금은 "무엇을 어떤 순서로 호출할지"를 코드가 결정**한다. 에이전트는 **LLM이 사용자 의도를 보고 어떤 도구를 어떤 순서로 쓸지 스스로 결정**한다. Tool Calling · RAG · 멀티모달 · LLM Evaluation 은 현재 전부 부재.

이건 결함이 아니라 단계의 문제다. 결정형 함수들이 잘 분리돼 있다는 점이 오히려 에이전트화의 발판이다.

## 2. 목표 아키텍처

### 2.1 레이어 위치 — Repository는 그대로 둔다

기존 설계의 핵심 불변식은 *"화면은 데이터 출처를 모른 채 `getRepository()` 인터페이스만 호출한다"* 이다. **에이전트 레이어는 이 불변식을 깨지 않고 Repository 위에 얹는다.**

```
화면(Server Component)
      │  getRepository() 인터페이스만 호출 (불변)
      ▼
┌─────────────────────────────────────────────┐
│  Repository (mock / live)                    │
│   - listThemes / getSpot / getCourse ...     │
│   - matchThemes  ←★ 여기를 에이전트로 위임     │
└─────────────────────────────────────────────┘
      │  matchThemes / planCourse 가 Planner 호출
      ▼
┌─────────────────────────────────────────────┐
│  Agent Layer (신규, 서버 전용)                 │
│   - Planner: LLM 에이전트 루프 (의도→도구→조합)  │
│   - ToolRegistry: 도구 카탈로그 + 스키마        │
│   - LlmProvider: LLM 호출 추상화 (mock/실키)    │
│   - Trace: 단계별 실행 로그 (Evaluation 입력)   │
└─────────────────────────────────────────────┘
      │  도구 = 기존 함수/API 클라이언트 래핑
      ▼
  scoreSuitability · estimateCongestion · reorderSpotsByCongestion
  getWeatherByCoords · getAirForStation · listGangwonItems · getItemDetail
```

화면도, Repository 인터페이스도 시그니처가 바뀌지 않는다. `matchThemes`/`getCourse` **내부 구현**만 에이전트 호출로 교체되고, 실패 시 기존 결정형 로직으로 폴백한다(회복력 원칙 유지).

### 2.2 도구 카탈로그 (Tool Catalog)

에이전트가 호출할 수 있는 도구는 **기존에 이미 존재하는 함수**를 LLM-friendly 스키마로 감싼 것이다. 새 비즈니스 로직을 만드는 게 아니라 **노출 방식**만 바꾼다.

| 도구 이름(안) | 래핑 대상 | 입력 | 출력 | 종류 |
|---|---|---|---|---|
| `list_themes` | `Repository.listThemes` | — | 테마 목록(id/제목/무드/태그) | 조회(정적) |
| `get_course` | `Repository.getCourse` | themeId | 코스 일정(items) | 조회(정적) |
| `search_pois` | `listGangwonItems` | 키워드/타입 | 관광 POI 후보 | 조회(API) |
| `get_weather` | `getWeatherByCoords` | lat,lon | 기온/강수/바람 | 조회(API·동적) |
| `get_air_quality` | `getAirForStation` | station | 통합대기 등급 | 조회(API·동적) |
| `estimate_congestion` | `estimateCongestion` | baseline,kind,at,날씨 | 혼잡지수·한산시간대 | 추론(순수) |
| `score_suitability` | `scoreSuitability` | 혼잡+날씨+대기질+kind | 적합성 0~100+사유 | 추론(순수) |
| `reorder_by_congestion` | `reorderSpotsByCongestion` | 하루 스팟+혼잡곡선 | 재정렬 결과 | 추론(순수) |

설계 메모:
- **읽기/추론만 노출**. 쓰기(저장·리뷰)는 1차 범위에서 제외 — 에이전트가 부작용을 일으키지 않게 안전 경계를 둔다.
- 각 도구는 **JSON Schema 시그니처 + 한 줄 설명**을 갖는다(프롬프트 엔지니어링 영역). 순수 함수는 네트워크가 없어 **테스트·재현이 쉬움** → 에이전트 회귀 테스트의 앵커로 적합.
- 도구는 `domain`(순수) / `server`(API) 출처를 메타로 표시 → 샌드박스(외부 egress 차단)에서는 `server` 도구를 자동으로 mock으로 대체.

### 2.3 에이전트 루프 (Planner)

표준 ReAct 형태의 다단계 루프. 매 스텝 LLM이 (a) 다음 도구 호출 또는 (b) 최종 답을 선택한다.

```
intent(자연어) ──▶ [LLM] 계획 수립
                     │  while not done and step < MAX_STEPS:
                     │    LLM이 도구+인자 선택 → ToolRegistry 실행 → 결과를 컨텍스트에 추가
                     ▼
                  최종 산출: { primaryThemeId, altThemeIds, plannedCourse, rationale }
                  + Trace(모든 스텝 기록)
```

가드레일: `MAX_STEPS` 상한, 도구별 타임아웃(http 헬퍼에 이미 존재), 동일 도구 반복 호출 차단, **전 과정 실패 시 결정형 폴백**(`matchThemes` 키워드 + 기존 `getCourse`).

## 3. 1차 타깃 — 코스 플래닝 에이전트

선택된 첫 슬라이스. 공고의 "Multi-step Agent"에 가장 직결된다. **여러 도구를 순차·조건적으로 엮어 하루 코스를 짜는** 흐름이기 때문.

### 시나리오 예시

입력: *"부모님이랑 2박 3일, 바다 보면서 안 붐비는 곳 위주로 느긋하게"*

에이전트의 다단계 추론(예시 trace):

1. `list_themes` → 후보 중 **해변/힐링** 테마가 의도("바다", "느긋")에 부합한다고 판단.
2. `get_course(theme=해변힐링)` → 기본 코스 일정 로드.
3. 각 스팟에 대해 `get_weather` + `get_air_quality` → 방문일 환경 파악.
4. `estimate_congestion` → "안 붐비는 곳" 제약을 만족하는지 스팟별 혼잡 확인.
5. 혼잡한 스팟 발견 → `search_pois` 로 인근 대체지 후보 탐색, `score_suitability` 로 비교.
6. `reorder_by_congestion` → 하루 동선을 한산한 시간대에 맞춰 재배치.
7. 최종: 조정된 코스 + **"왜 이렇게 짰는지" 자연어 근거**("부모님과 느긋한 일정이라 오전 한산한 시간대의 해변을 앞에 뒀어요") 생성.

여기서 **2~6번의 순서·반복·조건 분기를 코드가 아니라 LLM이 정하는 것**이 결정형 파이프라인과의 본질적 차이다. 같은 입력이라도 "붐벼도 좋으니 유명한 곳"이면 4~5번을 건너뛰는 식으로 경로가 달라진다.

### 인터페이스(안)

```ts
// apps/web/src/server/agent/planner.ts (신규, 서버 전용)
interface PlanRequest {
  intent: string;           // 사용자 자연어
  lang: "ko" | "en";
  date?: Date;              // 방문 기준 시각 (기본 now KST)
}
interface PlanResult {
  primaryThemeId: string;
  altThemeIds: string[];
  course?: Course;          // 재정렬·대체 반영된 일정
  rationale: LocalizedText; // 추천 근거(자연어)
  trace: AgentStep[];       // 단계별 도구 호출 기록 (Evaluation 입력)
}
```

`LiveRepository.matchThemes` / `getCourse` 가 이 Planner 를 호출하고, 실패 시 기존 결정형 결과로 폴백한다.

## 4. 키 없이 시작하는 전략 (샌드박스·비용 제약)

두 가지 현실 제약이 있다: (1) LLM 호출에 API 키·비용이 든다, (2) CLAUDE.md대로 **샌드박스는 data.go.kr·외부 egress가 막혀** 실호출이 안 된다.

그래서 **인터페이스 우선 + 주입식 Provider** 로 키 없이도 전 구조가 돌아가게 한다:

- `LlmProvider` 인터페이스 → 구현 2종: `MockLlmProvider`(시나리오 스크립트 기반 결정적 응답, 테스트·CI용) / `RealLlmProvider`(키 있을 때). `env`로 전환 — Repository의 mock↔live 패턴 그대로 재사용.
- `server` 출처 도구는 샌드박스에서 mock 데이터로 자동 대체 → 에이전트 루프 자체는 네트워크 없이 검증 가능.
- 실 LLM·실 API 검증은 기존과 동일하게 **로컬에서만** 수행.

이렇게 하면 에이전트 **오케스트레이션 로직**(루프·도구 선택·폴백·trace)을 LLM 키 없이 단위 테스트할 수 있다 — 결정형 함수 테스트 전략(현재 31개 통과)의 연장선.

## 5. 자격요건 매핑 & 확장 로드맵

| 공고 자격요건 | 에움길에서의 구현 지점 | 단계 |
|---|---|---|
| **Tool Calling** | §2.2 도구 카탈로그 + Planner 루프 | 1차(코스 플래닝) |
| **프롬프트 엔지니어링** | 도구 스키마/설명, 시스템 프롬프트, 근거 생성 | 1차 |
| **Multi-step Agent** | §3 코스 플래닝 루프 | 1차 |
| **LLM Evaluation** | `trace` 기반 추천 품질 평가 파이프라인(별도 슬라이스) | 2차 |
| **RAG** | 큐레이션·리뷰 텍스트 인덱싱 → 의도 매칭/근거 보강 | 3차 |
| **멀티모달(VLM/OCR)** | 관광지 사진 분석, 사용자 업로드 이미지로 의도 파악 | 4차(스트레치) |
| **제품화/운영 트러블슈팅** | 폴백·가드레일·캐시·trace 로깅(이미 일부 존재) | 전 단계 관통 |

→ 1차만 끝나도 자격요건 상위 3개(Tool Calling·프롬프트·Multi-step)를 실코드로 증명. 2차 Evaluation까지면 핵심 4개 충족.

## 6. 리팩토링 단계 (기존 Phase와 정합)

기존 Phase 1~4 골격을 건드리지 않고 **병렬 트랙**으로 추가한다.

- **A. 골격** — `server/agent/` 디렉터리, `ToolRegistry`·`LlmProvider`(mock)·`Planner` 인터페이스. 도구 8종 래핑. 네트워크·키 불요. *단위 테스트 추가.*
- **B. 배선** — `LiveRepository.matchThemes`/`getCourse` 가 Planner 호출 + 결정형 폴백. `EUMGIL_DEBUG=agent` 로 trace 로그. 화면 무변경.
- **C. 실 LLM** — `RealLlmProvider` + env 키. 로컬에서 실 API·실 LLM 통합 검증.
- **D. Evaluation** — `trace`/추천 결과 품질 평가 파이프라인(2차 슬라이스).

각 단계는 독립 머지 가능하고, A·B는 샌드박스에서도 검증된다.

## 7. 열린 결정 사항

구현 착수 전 정해야 할 것들(현재 미확정):

1. **LLM 프로바이더** — 어떤 모델/SDK를 `RealLlmProvider`로? (비용·툴콜 지원 여부)
2. **에이전트 범위 한계** — `matchThemes`만 위임할지, `getCourse` 전체 계획까지 위임할지(1차는 후자 권장).
3. **결정형 로직의 운명** — 폴백으로 영구 보존할지, 에이전트 안정화 후 축소할지. (권장: **영구 폴백** — 무중단·테스트 앵커)
4. **Evaluation 기준** — 추천 품질을 무엇으로 측정할지(제약 충족률 / 혼잡 감소량 / 근거 일관성 등).

## 부록: 핵심 불변식 (깨지면 안 되는 것)

- 화면은 `getRepository()` 인터페이스만 본다 — 에이전트는 그 **아래**에 숨는다.
- 외부 호출 실패 = 스팟/코스 단위 폴백, 화면 무중단.
- 공공 API·LLM 키는 **서버에서만**. `server/agent/*` 는 클라이언트 import 금지.
- 도메인 순수 함수는 그대로 유지 — 에이전트는 그것을 **도구로 호출**할 뿐 재구현하지 않는다.
