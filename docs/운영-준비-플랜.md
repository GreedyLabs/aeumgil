# 운영 안내

현재 운영의 실행·진단 기준이다. 초기 구축 계획은 제거했으며 제품 후속 과제는 [구현 현황](구현-계획.md), 값과 배포 절차는 [환경변수·배포](환경변수-배포.md), 실제 실행 증거는 [검증](검증.md)에 둔다.

## 1. 인증·설정

### 1.1 운영 기동 검사

[env.ts](../apps/web/src/lib/env.ts)의 `assertProductionEnv()`가 운영 프로세스에서 Auth.js/Keycloak 필수 인증 설정 누락을 거부한다. `next build`는 비밀값 없이 수행하고 런타임에 주입한다. 이 검사는 DB/API 연결 성공 검사와 다르다. 앱 전체 동작에는 배포 문서의 8개 값이 필요하다.

`AUTH_URL`을 운영 주소로 고정한 상태에서 프록시 뒤 Auth.js의 `trustHost`를 활성화한다. 개발 기본 인증값은 운영에서 사용하지 않는다. 설정 변경 전후 실제 주입 여부는 값 자체를 출력하지 않고 확인한다.

### 1.2 인증 서버

공용 Keycloak eumgil realm과 실제 Client/테마를 사용한다. 로그인, 앱 로그아웃, SSO 종료, 소셜 브로커는 서로 다른 상태를 가지므로 [인증·DB 안내](Phase4-인증DB-셋업.md)의 흐름대로 검증한다. 로컬 realm import나 초기화 명령을 운영 realm 변경 방법으로 쓰지 않는다.

## 2. 오류와 연결

- [오류 화면](../apps/web/src/app/error.tsx), [전역 오류](../apps/web/src/app/global-error.tsx), [404](../apps/web/src/app/not-found.tsx), 조회가 긴 화면의 loading UI가 있다.
- DB 연결은 lazy 생성, 연결 타임아웃 5초·풀 최대 10개다. DB 장애 때 인증/네트워크/스키마 오류를 구분한다. 카탈로그는 실제 DB가 필요하다.
- 외부 API별 부분 실패를 분리한다. 자료가 없는 경우 DB 기본정보와 미제공 안내를 남기며 날씨·관광·대기질을 모두 정상인 것처럼 표시하지 않는다.
- 워밍은 일부 자주 조회하는 날씨 격자·대기질을 백그라운드로 불러온다. 실패해도 기동을 막지 않으며 강원 모든 장소를 선조회하지 않는다.

| 증상                      | 먼저 확인할 것                                                                 |
| ------------------------- | ------------------------------------------------------------------------------ |
| DB 호스트 연결 실패       | 호스트/컨테이너에서 각각 라우팅·포트·로컬 네트워크 권한. 인증 실패 전인지 구분 |
| DB는 연결되지만 화면 오류 | `verify:db`로 현재 조회 테이블·컬럼과 `DATABASE_SCHEMA` 검사                   |
| API가 빈 값 또는 오류     | 활용 승인·Decoding 키·현재 오퍼레이션·원천 응답 코드, `verify:api`             |
| 로그인 Callback 오류      | AUTH_URL·Client ID·정확한 Punycode Callback·issuer                             |
| 테마/파비콘이 이전 모습   | 운영 Login theme·실제 CSS/아이콘 응답·CDN/브라우저 캐시                        |
| 재배포마다 첫 조회가 느림 | 캐시 볼륨 마운트·UID1001 쓰기 권한·캐시 load 상태                              |

## 3. 호출량과 캐시

### 3.1 요청 제한

목적 입력은 DB 테마 한 번 조회 후 순수 계산만 수행하므로 검색 자체에 LLM/동적 API 비용이 발생하지 않는다. [rate-limit.ts](../apps/web/src/server/rate-limit.ts)에 IP별 토큰 버킷 유틸리티(버스트 10, 분당 10)가 남아 있지만 현재 검색 경로에서는 사용하지 않는다. 향후 고비용 진입점을 추가할 때는 유틸리티 존재만으로 제한이 적용된 것으로 간주하지 말고 실제 배선을 확인한다. 외부 프록시·DB를 포함한 전체 서비스 제한은 별도다.

### 3.2 현재 TTL

| 데이터                                     | TTL    |
| ------------------------------------------ | ------ |
| 날씨·강원 대기질                           | 30분   |
| 고속도로 소통                              | 5분    |
| 자외선·행사 목록                           | 1시간  |
| 관광지 일별 집중률 예측                    | 6시간  |
| 관광지/행사 상세·무장애 상세·방문자수      | 24시간 |
| 언어별 관광 목록·상세·관광사진·오디오/대본 | 24시간 |

동일 키의 진행 중 요청을 합친다. 정상 빈 응답도 캐시하고 실패에는 재호출 대기 시간을 둔다. 날씨는 좌표별이 아닌 기상 격자 키, 대기질은 강원 측정소 목록을 재사용한다. 카탈로그 검색과 목록은 DB를 사용한다. 외국어는 언어별 공식 목록 캐시를 공유해 국문 정본과 연결하며 카드마다 API를 요청하지 않는다. 개인 코스의 음식점/숙소 검색은 언어별 공개 DB 목록을 5분간 서버 메모리에 캐시하고 동시에 들어온 조회를 합친다. 이 메모리 캐시는 API 파일 캐시와 별도이며 사용자 기록·검색 문장은 저장하지 않는다.

API 활용 계정에서 각 서비스의 현재 허용량과 실제 사용량을 확인한다. 특정 호출 시간이나 과거 통과율을 지속 성능으로 일반화하지 않는다.

## 5. 배포 인프라와 관측

### 5.1 영속 캐시

[cache.ts](../apps/web/src/server/cache.ts)는 메모리와 파일의 두 계층이며 **단일 앱 인스턴스** 전제다. `/app/cache` named volume과 UID1001 쓰기 권한을 유지한다. 다중 인스턴스가 같은 파일을 쓰면 서로 덮어쓸 수 있으므로 수평 확장 전에 `CacheStore`를 Redis/DB 등 공유 저장소로 바꾼다. 레이트리미터도 함께 공유해야 한다.

### 5.2 Health·로그

`/api/health`는 프로세스, `/api/health?deep=1`은 DB·캐시 상태를 검사한다. 캐시 항목 수가 0인 신규 인스턴스가 반드시 장애인 것은 아니다. 외부 API 요청 자체를 health 검사마다 반복하지 않는다.

`EUMGIL_DEBUG=http,cache,repo`로 HTTP/캐시/Repository 상세 로그를 켠다. 기본은 조용하게 동작하고 경고는 별도로 남는다. 비밀값·토큰·쿠키를 출력하지 않는다. 사용자별 요청 추적·장기 오류 집계는 별도 운영 개선 과제다.

### 5.3 백업·복원

카탈로그 수집 전 스냅샷은 해당 변경 복구를 위한 보조 자료다. PostgreSQL 사용자 데이터와 인증 DB의 정기 백업을 대신하지 않는다. 운영 백업 보관 위치·주기·복원 책임자를 정하고 별도 DB로 복원해 검증해야 한다. 이 문서는 정기 백업 또는 복원 훈련이 완료됐다고 보증하지 않는다.

## 7. 사용자 데이터와 서비스 안내

### 7.1 원천 정보

서비스의 `/doc?type=sources`와 상세 사진 캡션에서 출처를 제공한다. 사진·설명·데이터를 추가할 때 원천별 사용 조건을 유지한다. 자료가 없으면 무관한 사진이나 가상 수치를 채우지 않는다.

### 7.2 계정 탈퇴

앱 DB의 개인 코스·추천 보관·리뷰·방문·취향·프로필을 삭제하고 Keycloak 계정 삭제를 시도한다. 관리 Client가 없거나 실패했으면 `sub` 기준의 수동 인증 계정 정리가 필요하다. 사용자에게 자동 삭제 완료로 오인시키지 않도록 현재 처리 결과와 후속 경로를 확인한다. 운영 문의처·안내 문구는 실제 처리 책임과 맞춰 유지한다.

## 8. 릴리스 검사

### 8.1 자동·브라우저 검사

타입·단위 검사는 GitHub Actions 게이트다. 브라우저 검사는 실제 DB가 필요한 별도 실행이며 인증 픽스처를 사용하는 앱 검사와 실제 인증 서버 검사를 구분한다. 실행·정리 방법은 [검증 안내](검증.md)를 따른다.

### 8.2 배포 후 사용자 흐름

홈 목적 입력 → 추천 → 개인 일정, 탐색 카드/지도/상세, 행사·무장애 안내, 내 여행 재조회, 로그인 복귀를 PC와 모바일에서 확인한다. 긴 제목·결과 없음·느린 응답·저장 실패·다른 탭의 변경도 점검한다. 가로 넘침 0만으로 시각 점검을 대체하지 않는다.

### 8.3 CI·운영 이미지

Actions 검사·GHCR 빌드·웹훅 성공 뒤 실제 컨테이너의 image revision과 healthy를 확인한다. 웹훅 성공만으로 최신 이미지가 실행 중이라고 결론내리지 않는다. 결과는 [검증 기록](검증.md)에 남긴다.
