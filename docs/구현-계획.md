# 에움길 구현 계획 (Implementation Plan)

> 화면 디자인·플로우가 프로토타입으로 완성된 상태에서, 제안서가 요구하는 실제 동작
> 서비스로 발전시키기 위한 단계별 계획.

> **확정된 방향 (2026-06-20)**
> - **제출 범위:** 공모전에 **전체 실연동 · 실제 운영 서비스**로 제출 — mock 시연 없음.
>   모든 공공 API를 실제로 붙이고 DB·인증까지 운영 가능한 상태로 완성한다.
> - **자연어 매칭:** **키워드 규칙으로 먼저 구현**하고, 개발이 어느 정도 완료된 뒤
>   **LLM 분류 도입을 검토**한다(필수 아님).

  ([apps/web/src/design/App.tsx](../apps/web/src/design/App.tsx))

| 항목 | 현재 (프로토타입) | 목표 (실서비스) |
|---|---|---|
| 라우팅 | `App.tsx` 안의 `useState` 상태머신 | 실제 Next.js URL 라우트 |

| 저장/리뷰/방문 | 메모리 `Set` | DB 영속화 |

## 1. 데이터 성격 분류 (가장 먼저 합의할 설계 기준)

제안서의 데이터를 **갱신 주기**로 나누면 구현 전략이 분명해진다.

1. **정적 큐레이션 데이터** — 거의 안 바뀜, 사람이 설계
   - 6개 특화 테마, 테마↔코스 매핑, 대체지 매핑, 자연어 키워드 규칙
   - → 코드/JSON 또는 DB의 시드 테이블로 관리. 외부 API 불필요.
2. **반정적 관광 자원 데이터** — 가끔 갱신, 외부에서 수집
   - 관광지·행사·음식점·숙박 기본정보(이름/위치/이미지/타입/좌표)
   - → 한국관광공사 국문관광정보 API에서 **배치로 수집해 DB에 적재**, 캐시 활용.
3. **실시간 동적 데이터** — 요청 시점마다 달라짐
   - 혼잡도/집중률 예측, 날씨, 대기질, 생활기상지수, 교통 정체
   - → 요청 시 서버에서 API 호출 + **단기 TTL 캐시**.
4. **사용자 데이터** — 회원·개인화
   - 계정, 저장, 리뷰, 방문기록, 온보딩 선호
   - → DB에 영속화, 인증과 연결.

> 이 분류가 이후 모든 단계(스키마, 캐싱, 화면 데이터 소스)의 기준이 된다.

### Phase 3 — 핵심 로직 (서비스 차별점)
**목표:** 제안서의 4대 기능을 실제 알고리즘으로 구현.

- [ ] **자연어 → 테마 매칭**
  - 1차: 현재 키워드 규칙 고도화(동의어·가중치)
  - 확장(선택): LLM 분류로 의도→테마 매핑 정확도 향상
- [ ] **방문 적합성 스코어** (현재 mock 고정숫자를 실제 산출로)
  - 입력: 혼잡도/집중률 예측 + 날씨 + 대기질 + 생활기상지수 + 교통
  - 출력: 0~100 적합성 점수 + 사유(예: "강풍·미세먼지로 산악보다 내륙 추천")
  - 테마별 가중치 다름(해변=자외선/바람 민감, 산악=강수/강풍 민감 등)
- [ ] **혼잡 분산형 대체지 추천**
  - 선택지가 혼잡할 때 같은 테마·인근에서 적합성 높은 대체지 산출
  - 현재 `ALT_SPOTS` 정적 매핑 → 실시간 혼잡도 기반 동적 산출로 확장
- [ ] **조건 반영형 코스 선별**
  - 일정/이동수단/체류시간/테마 입력 → 사전 설계 코스 중 적합 동선 선별·재정렬

### Phase 4 — 데이터베이스 & 회원/인증
**목표:** 사용자 데이터 영속화와 실제 로그인.

- [ ] DB 선택 (예: PostgreSQL + Prisma) 및 스키마

- [ ] 저장/리뷰/방문 기록을 Server Action으로 DB 연동
- [ ] 온보딩(페이스·동행·관심테마) 저장 → 추천 개인화에 반영

## 3. 권장 진행 순서 (가장 빠르게 "동작하는 실서비스"까지)

> 큰 위험을 먼저 줄이는 순서. 화면은 이미 있으므로 **데이터·로직 신뢰성**이 관건.

1. **Phase 0 + Phase 2의 API 1종(국문관광정보) 스파이크**
   — 서비스키로 강원도 관광지 실제 수집이 되는지부터 검증(공공 API는 키 승인·쿼터·
   응답 품질 리스크가 크므로 가장 먼저 확인). 전체 실연동이 확정됐으므로, 이 스파이크
   직후 **7종 API 전부의 키 발급·승인 절차를 병렬로 착수**해 승인 대기 시간을 줄인다.
2. **Phase 1 라우팅 전환** — mock 유지한 채 실제 URL 구조로 이전.
3. **Phase 3 적합성 스코어 + 동적 데이터(날씨/대기질/혼잡도) 연결** — 핵심 차별점 완성.
4. **Phase 4 DB·인증** — 저장/리뷰/개인화 영속화.
5. **Phase 5 품질·배포.**

## 4. 결정 사항 & 남은 확인 사항

### 확정됨
- ✅ **제출 범위**: 전체 실연동 · 실제 운영 서비스. 7종 공공 API를 모두 실제 연동하고
  DB·인증까지 운영 가능 상태로 완성 → **Phase 2 API는 선택이 아니라 전부 필수**.
- ✅ **자연어 매칭**: 키워드 규칙 우선, 개발 후반에 LLM 분류 도입 검토.

### 아직 정할 것
- **DB/호스팅 선택**: PostgreSQL+Prisma / Supabase / 기타
- **인증 범위**: 4개 소셜(카카오·네이버·구글·애플) 전부 vs 카카오·네이버 우선
- **이미지 자산**: 한국관광공사 이미지 API 우선 사용(실운영이므로 Unsplash 직링크는 제거 대상)
